# 本地状态与恢复

`HubStore(directory:)` 打开传入数据目录下的 `agent-hub.sqlite3`。正式应用由启动层解析 Application Support 目录，测试为每个案例使用临时目录。数据库使用系统 SQLite、外键、WAL 和 FULL 同步。单一调度实例通过目录内的 `owner.lock` 持有内核文件锁。进程退出即释放锁，残留的文件本身不会阻止下次启动。

## 表与索引

| 表 | 用途 |
| --- | --- |
| projects / config | 规范化项目路径、Git 画像、全局和项目配置 |
| tasks | 任务聚合，包括与工作项关联的尝试、进程身份、交接、工作区、产物引用及验证记录。项目、优先级和更新时间用于看板排序 |
| requirements / plans | 需求的目标与验收、每次计划首次保存时的完整分工。工作项当前状态在 tasks 内更新 |
| messages / drafts | 消息由稳定 ID 去重。目标角色、任务与会话在发送时确定。草稿按任务 ID 与接收者分别保存 |
| events / event_counters | 可分页的活动流，由数据库分配顺序号。迟到输出引用原尝试的需求、计划和执行代数 |
| requests | 对创建任务、修改任务的重复请求记录操作和任务 ID |

`updateTask` 在 `BEGIN IMMEDIATE` 事务中加载最新状态，执行调用方的校验和更改，再同时写入业务状态、修订记录、活动事件和请求回执。重复请求返回当前记录。调度器在此闭包内检查本次工作的代数、预算和有效性。数据库同时拒绝身份变更、修订倒退和取消后重开任务。首次进入运行中时固化生效配置，暂停及待处理时间不计入运行时长。处于运行状态时机器休眠的墙钟时间计入任务时长。

配置按全局、项目、任务的顺序覆盖，角色、模型和并发按对应键继承。更换角色的 provider 会清除原 provider 对应的模型。命令使用 argv，空数组可以停用继承的命令。敏感类型的环境变量在保存前被拒绝。用户文本、事件、草稿和业务记录的字符串字段在写入前应用凭据模式过滤。诊断导出仍须使用允许字段列表，路径、提示、环境变量及命令输出均可能包含私人数据。

## 分页与保留

事件和消息可从顺序号向后增量读取，或者从最新页向前翻页。每次返回 1–500 条、按时间序排列。消息和业务记录保留至数据目录删除。单条活动详情最多保存约 8 KiB，活动流按任务在每 128 条新事件时裁剪至最近 4096 条。删除的 SQLite 页面可供后续写入复用。事件顺序号可能因其他任务或清理出现间隔；UI 可重新载入任务快照，并从最新一页继续阅读。业务上的验证、交接和尝试保存在任务记录中。凭据模式过滤不能识别无上下文的任意字符序列，API key 通过独立的钥匙串接口处理。

## 升级与异常退出

迁移定义在 `Sources/HubKit/Store.swift` 的 `migrate(from:)` 中。schema 版本由 `PRAGMA user_version` 控制。升级现有版本前，SQLite 在线备份 API 将包含已提交 WAL 数据的一致副本写入同目录的 `before-v<N>-<UUID>.sqlite3`。迁移在单个事务中完成，写入错误会回滚。版本高于本应用支持范围时，启动返回明确错误。恢复备份时先退出持有此目录的应用，将备份放入一个新的空数据目录，命名为 `agent-hub.sqlite3` 后再打开。

打开数据库不会重新派发任务。应用先通过 supervisor 核对本次受管进程的身份，随后调用 `recoverInterrupted()`。无法重新连接的尝试进入 interrupted 并记录原因，未完成的任务进入 needs_user，标记 resume_required，递增执行代数。恢复扫描可重复运行。历史产物、代码工作区、已提交的消息和草稿保持可读取。

真实 SQLite 事务、并发重放、关闭再打开、分接收者草稿、游标分页、升级前备份及未来 schema 拒绝路径由 `Tests/HubKitTests/StoreTests.swift` 覆盖。

## 看板读取成本

控制器先读取连接的 changeCounter。有写入时，taskUpdates(known:) 用任务 ID 与更新时间的索引找出变化，再解码这些任务的完整记录。流输出和草稿写入只触发轻量检查。分组事件与角色消息查询直接接受游标，支持向前翻页。

2026-11-26 在 Apple Silicon 的本地 Debug 测试中，151 张任务卡连续读取 20 次，全量解码平均 9.94 ms，仅检查无变化任务平均 0.07 ms。相同测试另写入 4400 条流事件，保留 4145 条。这些数值来自合成数据，覆盖数据库读取与裁剪，不包含 SwiftUI 绘制或真实 CLI 延迟。可通过 StoreTests.testIndexedRefreshAndBoundedStreamWithHistory 复测。

配置解码允许较旧的记录省略新增选项。遇到无法识别的配置字段时会报告字段名，用户可使用兼容版本继续打开原记录。需要确认是否仍有用户消息时，调度器可以在 updateTask 的同一事务中读取 pendingUserMessages。完成之后到达的新输入会保留原草稿，提示通过需求修改或后续任务继续。

角色活动流在 SQL 分页前按 provider 文本片段的稳定标识选取最新快照，消息送达状态由消息本身展示。原始活动分页仍可查看各次采样。HubTask.providerSessions 按 provider 与 CLI 返回的会话编号聚合持久化的尝试，记录首次和最近观察时间，以及实际关联的尝试。相同的 CLI 会话编号在不同 provider 间独立。

Schema v3 新增可空的 events.provider_type，保留适配器提供的原始事件类型（脱敏后最多 128 UTF-8 字节）。messages 的业务数据新增可选的 attemptID 和 finalStreamGroup。final_streams 表将最终消息与实际发送它的尝试、确切流分组关联。角色活动分页会在取游标前过滤这一分组，其他流和工具动作照常显示。原始事件及消息均保留。

v2 升级时，旧消息没有这些新字段。迁移仅在角色、工作项、需求版本、已保存的完成摘要、可得会话标识及唯一结束时间窗口全部对应时建立关联，并要求该次尝试最后一条文本快照与回复开头或结尾一致。无法唯一匹配的记录继续显示。升级前会创建原库的一致备份。
