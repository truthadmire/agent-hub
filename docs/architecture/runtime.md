# 执行、恢复与验收

一次用户任务对应一个受管集成分支。每次规划、执行、修复或改派都会创建独立的 Attempt 和工作树。调度器只操作 Git 服务登记的工作树。用户在原项目已有的修改由建任务时选择的提交或已预览的快照决定。

## 从任务到代码

1. 启动时合并任务、项目与全局配置，并把实际配置存入任务。SQLite 保存需求版本、计划版本和执行代次。重复点击启动只会保留一次派发。
2. 角色映射只有一个可用工具时，程序生成一项实施任务。多个工具可用时，负责人以只读 CLI 回合输出结构化计划。解析器检查角色、ID、依赖、路径与写入所有权。并行写入范围须彼此独立，有重叠的工作须声明先后关系。用户的预算与权限始终由应用配置决定。
3. 任务队列按优先级和等待轮次调度。全局并发、每个任务并发，以及跨任务共享的 provider 并发均参与派发。实际账号限额未知时，单个 provider 默认为一个并发。
4. 程序先保存 Attempt 和预期工作树，再通过启动回调保存 PID、进程组、可执行文件、启动时间、系统启动会话等身份信息。处理标准输出和错误流的增量事件，并将最终模型回复保存为消息。会话 ID 是来源证据，进程中断后的继续策略是从已核对的代码检查点启动新会话。
5. 程序提交受管工作树，依据实际 Git 差异检查本次写入边界。所有上游结果先串行整合，再派发依赖项。带目标和待送达状态的用户消息在适合的轮次送达。实现结束后才收到的消息会生成后续工作项，完成事务再次核查当前修订的消息队列。
6. 若程序在 Git 整合后、SQLite 更新前退出，恢复时核对原任务 HEAD、尝试 HEAD、工作树清洁状态和直接合并关系。已整合的结果可以恢复确认。真正发生冲突时保留双方工作树和 MERGE_HEAD。用户在受管集成工作树解决并暂存冲突后点击继续。

## 用量与错误

每次派发计为一次 Hub 尝试。协议报告的输入/输出 token 是每个尝试的独立快照。内部模型调用次数、货币及订阅余额缺少可信来源时保持未知。用户主动选择并授权 DSH 后可以使用自有 API key，自动改派到收费来源还须另行允许该提供商作为备选并设置金额策略。未结算调用计入后续派发判断；金额阈值不会终止已发出的服务端请求。

短暂网络错误和限流适用有上限的退避。认证、权限、真实协议错误会保留当前成果并请求处理。修复、重试、切换和累计运行时间在数据库中保存，重新打开程序后继续计数。没有稳定的服务端重试时间时，程序使用自身的有限退避。

## 快照与验收

验证命令来源为项目设置和受控的 manifest 检测。模型计划里的任意命令作为说明保存。程序先在独立工作树上运行已有基线检查，再在实际集成工作树运行交付检查。每项保存命令、工作目录、工具和系统版本、时间、退出状态、去敏输出与源码版本。源码树在验证前后都计算树 ID。检查产生源文件变更时，保存新提交和 patch，并从新的交付快照重新检查。持续修改源码的检查会阻止自动完成。

程序按需求修订与集成提交核查每项必需验证。自由文本验收条目须有人工确认。没有自动检查或没有源码差异时，程序也会要求人工检查。已有失败可以触发有上限的修复；相同失败指纹或相同快照再次失败时停止。受环境阻塞的必需检查可在补全环境后重跑，或由用户针对当前版本明确豁免并记录理由。标为完成还要求所有工作项已整合，相关 patch 可访问，且没有待处理的用户消息。

## 暂停、取消和恢复

暂停先停止派发，再等待进程组收尾和代码检查点保存。取消先更新执行代次，再停止进程。迟到的输出和局部成果仍归属于对应尝试，旧代次不能整合或完成当前任务。改动需求或共享接口时增加需求、计划和执行版本，并重新规划。

重启后先核实旧进程身份，应用恢复为需要用户继续。点击继续时，程序只从可确认旧写入者已经退出的工作树保存中断成果，并重新验证需求与范围。仅恢复上次已交付的步骤时会另外核对实际 HEAD、写入范围及当前计划。恢复不能证明安全时保留旧工作树和诊断信息。

动态预览仅可在没有活动执行的成果任务中启动；暂停任务可以查看静态预览。进入新一轮执行或重新验证前停止受管预览。Git worktree 隔离文件变化，CLI 自身的沙盒能力和验证执行器的 macOS 沙盒负责相应进程的实际访问约束。
